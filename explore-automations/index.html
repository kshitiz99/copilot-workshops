Duration: 15 minutes

From issue to action

So what Start a Copilot session straight from a GitHub issue. The issue becomes the session’s starting context, so Copilot begins with the right problem.
1Start from your repository

In the Copilot app, find your tailspin-toys repository under Sessions. Click the highlighted Create from… icon beside its name to begin.

2Choose your issue

Select Issues in the pop-up, then click the issue you want to tackle with Copilot.

3Ask for a plan before any code

Your new session opens with the issue already attached. Ask Copilot to think before it codes: it researches the issue and your repository, then returns a plan for your approval.

  • Approach
  • Implementation steps
  • Potential risks
  • Expected outcomes
  • Your approval first

What you’ll see in the recording

  1. The issue comes with you — Copilot prepares a dedicated worktree and starts the session with Issue #164 attached above the composer and open beside the chat.
  2. Copilot commits to planning first — It promises to review the issue, its comments and artifacts, and the relevant code, then prepare a plan—without changing repository code before your approval.
  3. It gathers the evidence — Copilot reads the issue with gh issue view, inspects the worktree and checks project guidance such as copilot-instructions.md, README.md, CONTRIBUTING.md and SECURITY.md.
  4. It studies the code and tests — It opens the affected implementation and test setup, including extension.mjs, package.json and vitest.config.ts, and loads relevant skills such as quality-checks.

This recording shows the submitted prompt and Copilot’s initial research, not the finished plan or approval.

Your session may read different files, depending on the issue you chose.

Checkpoint Review before you approve

Expect a plan covering the approach, implementation steps, potential risks and expected outcomes. Copilot waits for your go-ahead before implementing anything.

4Review the plan. Give Copilot the go-ahead.

Read the full plan in the right-hand Plan tab before deciding. The task list is only a summary: scroll through the problem and intended outcome, confirmed scope and decisions, and the evidence from the current checkout.

A practical review checklist

  • Does it solve the issue? Check the problem statement and intended outcome against what you need done.
  • Is the scope right? Look at the confirmed decisions and out-of-scope work. Make sure the plan stays focused and respects any boundaries.
  • Will the approach work? Review the implementation and test strategy, including how it handles important edge cases.
  • Are risks and dependencies covered? Check assumptions, compatibility and anything that could block or change the work.
  • How will you know it succeeded? Look for concrete validation and success criteria, not just a list of files to edit.

In this example, the five tasks move from extracting the production query policy and wiring the extension test harness through boundary and database-entry-point coverage, then documentation and validation. That sequence is specific to this regression-coverage issue; another issue may need different files, tests or dependencies.

Choose what happens next

  1. Ready to proceed? In the Review plan panel at the bottom, select Approve and implement this plan, then click Continue.
  2. Need more work on the plan? Do not approve it yet. Choose Exit plan mode and I will prompt myself to return to the session. Give Copilot your feedback in the chat and ask it to revise the plan; review the update before approving.

Approval authorizes Copilot to implement the reviewed plan; it does not automatically merge or deploy the changes, or guarantee they are correct. Review the resulting changes and test outcomes before deciding what to do next.

Duration: 20 minutes

From code to merge-ready PRs

So what Make your changes easy to understand, review and trust. A focused, validated pull request is ready for a merge decision—not an automatic merge or deployment.

Once Copilot has implemented your approved plan, the next goal is a pull request (PR): a proposal to review the changes on your branch before merging them into the target branch. It connects the work back to the issue and gives reviewers a clear place to understand, discuss and evaluate what changed.

Merge-ready means more than code that runs. The changes should address the issue and agreed scope, with a review for correctness and unrelated edits. Relevant tests and required automated checks should pass, reviewer feedback should be addressed, required approvals should be in place and merge conflicts should be resolved. Together, these give your team evidence for a confident merge decision.

A clear PR summary explains what changed, why, how it was validated and any remaining risks. Copilot can help refine the changes, test them and explain the results, but AI output or green checks alone do not guarantee readiness. Repository rules and human review still govern the decision. The outcome is a focused, understandable, validated PR ready for review and a merge decision—not an automatic merge or deployment.

1Turn approved work into a pull request

When Copilot finishes the approved work, click Create PR at the top of your session. Not ready for review yet? Open the arrow beside it and choose Create draft PR instead.

Once it’s created, the PR opens right beside your session—linked to your issue, with a full description for reviewers. It’s now open for review, not merged.

  • Open · your branch → main
  • Linked issue
  • Description & changed files
  • Checks & reviews
2Invite Copilot to give your PR a review

With your pull request open, request a review from the Copilot Code Review agent. Review its feedback, make any needed updates, and confirm the required checks and approvals—then your PR is ready for a merge decision on main. Copilot’s review is helpful input, not an automatic merge or a guarantee of readiness.

Duration: 25 minutes

From repeat work to automated workflows

So what Describe it once. Let Copilot pick up the repeat work. Turn a weekly release-notes chore into a reviewable pull request—without handing over the merge decision.

An automation is a reusable task Copilot can start on a schedule, in response to an event or on demand. Instead of opening a chat and pasting the same prompt every week, save the task once and let its trigger start each run. Every run still needs the right access and clear instructions; saving an automation does not guarantee it will succeed.

1Trigger: when

A weekly time, a repository event or a manual start tells Copilot when to begin.

2Instructions: what

Your prompt defines the job, its boundaries and the result you expect from each run.

3Tools: what it may do

Allow only the capabilities needed, such as reading PRs and proposing a changelog update.

The selected repository supplies the working context. Local runs need your computer and app available; cloud runs can start while your laptop is off, subject to repository policies, authentication and available resources. For this example, you need write access and the repository’s Copilot cloud agent and automation policies enabled. Available settings can vary by account and organization.

Friday release notes, delivered as a PR

Give developers, leads and PMs an understandable summary of the week: take recently merged work, group it into plain-language notes, add a dated section to CHANGELOG.md and open a pull request for review. If nothing was merged, report that instead of opening an empty PR. People still review the notes, changed files and checks before any merge.

1Give your weekly task a home

Open Automations in the sidebar, click + New automation at the top right, then choose Create manually. Some versions call the entry button Create automation.

In Manual automation creation, enter a recognizable name such as Weekly Friday Release. The name is a label, not a schedule: writing “Friday” here does not choose the day of the run.

2Set Friday and allow only the tools you need

Switch Trigger from Daily to Weekly. Choose Friday in Day of week and a suitable Time of day. Enable Run in the cloud if you want it to run without your laptop being on.

Recording note: the example leaves Monday selected, despite its Friday name. For this workshop, explicitly choose Friday. The recorded 9:00 AM India-time selection appears on the saved card as Mon 3:30 AM UTC. Confirm your timezone and the final card’s schedule; do not assume every time field is UTC.

For a cloud run, open Tools and select the capabilities this release-notes task needs. The following are recommended picks, not a claim that the recording selected them all:

  • Search PRs — find pull requests merged into the default branch during the last seven days.
  • Read PR — understand each change and collect its link and author.
  • Get file — read the existing CHANGELOG.md before adding notes.
  • Commit and push changes — save the changelog update on a branch.
  • Create PR — propose that branch’s notes for review.

The clip searches tools for issues and pull requests, but the final form says 1 tool selected. That is not evidence of a complete permission set. Check your selections against the task above; Merge PR is not needed.

3Tell Copilot exactly what each run should deliver

The prompt fixes the time window and categories, asks for readable lines with traceable PR links and credits the authors. It defines the deliverable as a dated changelog section and a reviewable PR, with a no-merge/no-PR fallback. Copilot should replace <date> in the title with the appropriate date for the release-note week.

Even Personal cloud automation prompts and session logs are visible to repository readers. Never include secrets or sensitive information in these instructions.

4Save it, test a run and review the result

Choose your own Repository with write access, then select an available model and agent using the controls below the prompt. The clip uses a repository named SE-COCKPIT; it is just an example, not a workshop requirement.

For cloud automations, choose Personal or Shared under Type. Personal automations use your identity and credits; Shared automations are visible to people with repository access and use Copilot’s identity with credits charged to the repository owner. Choose deliberately: type cannot be changed after creation.

Optionally expand AI credit limits to set per-run and daily limits appropriate to your budget. Review the repository, tools, scope and Friday schedule before saving: only the release-note change to CHANGELOG.md is expected, not unrelated code edits or an automatic merge.

Click Create to save. To save and test immediately, open its dropdown and choose Create and run. The recording reveals that option but actually saves with Create. Its final Idle card confirms saved configuration only; check the displayed day, time and repository.

When ready, test the saved automation using the card’s play button. Open the resulting run to inspect its status and logs. If it creates a PR, review the notes, links, authors, changed files and required checks before deciding whether to merge. If there were no merges, expect a message and no PR; errors or a saved card alone are not successful output.

Before a repeat manual run, check for an existing release-note PR or dated section for the same week to avoid duplicate notes. Test the configuration before relying on its weekly schedule.

Checkpoint Scheduled correctly. Scoped carefully. Reviewed by you.

Confirm Friday, the timezone, repository and task-specific tools. A saved automation is the beginning; a successful run and a reviewed PR are the evidence that the workflow works.

From unfamiliar code to meaningful tests

The takeaway Understand first. Audit with evidence. Add tests that prove behaviour. Copilot helps investigate and implement. You review the evidence, choose the gap and check the results.

The loop you can reuse

Run → Map → Audit → Choose → Test → Verify

Repeat for the next behaviour or area that needs deeper inspection.

Before you finish Show the evidence, not just the output
  • Show the running app and explain one path through it.
  • Trace a codebase document's finding back to its source.
  • Explain one confirmed test gap and the regression a proposed or added test would catch.
  • Show the focused test results, or clearly state what could not run and why.

No measured before-and-after coverage? Do not claim a percentage improvement. Describe the behaviour now protected and any work still outstanding.
